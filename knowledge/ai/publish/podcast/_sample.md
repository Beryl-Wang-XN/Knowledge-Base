# 口播稿 · Prefill 便宜，Decode 贵

样例只覆盖一个知识点，短于正式每日稿。正式每日稿按当天卡片写到可朗读 20–30 分钟，不另编事实。同目录 `_sample.m4a` 由 `scripts/synthesize_podcast.py` 用晓晓合成，分段标题不朗读。

## 【开场】

今天只讲一件事：大模型推理为什么要分成两段，以及这跟 token 报价有什么关系。

你平时看到的输入价和输出价，不是两套随手写的数字。它们对应两次完全不同的计算。

## 【两段分别在干什么】

第一段叫 Prefill，预填充。你把一整段提示放进去，模型把这 N 个 token 一次并行算完，顺手留下缓存，并给出第一个输出 token。这段活又大又齐，GPU 的算力吃得满，所以它是计算密集。你感觉到的，是等多久才看见第一个字，也就是 TTFT。

第二段叫 Decode，解码。从第二个输出 token 开始，每一步只处理一个新 token，但每一步都要把整个模型的权重，加上已经攒下的缓存，从显存里再读一遍。算的很少，搬的很多，瓶颈变成显存带宽。你感觉到的，是后面每个字要等多久，也就是 TPOT。

整次请求的延迟，大约就是：首字等待，加上每个后续 token 的时间乘以输出长度。输出越长，后半段越主导时间和成本。

## 【这和定价什么关系】

所以「输出比输入贵」有技术来源。Decode 是串行的，一张卡会被这一次生成占住更长时间。输入长、输出短的请求，比如把一篇长文收成一句话，压力在 Prefill。短提示写长文、写长代码，压力在 Decode，也更贵。

组 batch 也不是两段一样划算。Decode 卡在带宽，把多个请求拼在一起，权重搬运可以摊薄。Prefill 本身已经把算力吃满，拼批的收益是另一回事。

如果平台能把这两段拆到不同的机器上分别优化，这就是 PD 分离。它值得当成降本方向看，而不是当成一个名词放过。

## 【收束】

下次看一个新场景，先问两句。它主要在等第一个字，还是在等后面那一长串字？它吃的是算力，还是吃带宽？问完，报价和采购才对得上那次请求真正占用的资源。
